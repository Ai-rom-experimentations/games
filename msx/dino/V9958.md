# The V9958 target: what it takes to move CHROME DINO up a generation

This is the working note for the retarget the player asked for: **the highest
graphics level an MSX has**, which is the V9958 (MSX2+/turbo R) driving a
512x212 16-colour bitmap with hardware scrolling.  It is not done - this file
is the map, and the facts below are the ones that cost the most to get wrong.

The MSX1 cartridge in this folder is untouched and still builds and checks;
the V9958 version is a second target, not a replacement, until it is finished.

## Why this is a rewrite and not a graphics swap

Graphics II gave us a tile engine: 192 patterns, a name table, per-tile
colour.  A bitmap screen has none of that - every pixel is ours, there is no
name table, no colour table, no third-bank trickery (which is the bug the
MSX1 version currently has), but also no free scrolling and no free sprites
on top of a tile layer.  What we get instead:

| | MSX1 Graphics II | V9958 512x212 |
|---|---|---|
| colours | 16, two per 8x1 strip | 16 per pixel out of 512 |
| how the picture is stored | name table + patterns + colour table | one byte per two pixels |
| scrolling | move the name table by hand | R#23 vertical, R#25-R#27 horizontal |
| objects | sprites (32, 4/line, 16x16) | sprites (32, 8/line, 16x16) |
| text | tiles | our own blitter |

## The facts, with sources

**Address of a pixel in GRAPHIC 6 (SCREEN 7, 512x212, 16 colours):**

    ADR = X/2 + Y*256

Two pixels per byte, high nibble first.  212 lines x 256 bytes is 54,272 bytes,
so a screen fits inside the 128 KB VRAM.  (The MSX2 Technical Handbook gives
`X/2 + Y*128` for GRAPHIC 4/SCREEN 5 and `X/4 + Y*128` for GRAPHIC 5/SCREEN 6,
chapter 4 section 3.6/3.7; GRAPHIC 6 is the same line of thought with twice
the bytes per line.)

**Vertical scroll:** R#23 = the line of the 256-line page shown at the top
(MSX Wiki, VDP Display Registers).

**Horizontal scroll (V9958 only):** the offset is nine bits, HO0-HO8:

    R#26: 0 0 HO8 HO7 HO6 HO5 HO4 HO3
    R#27: 0 0 0   0   0   HO2 HO1 HO0

R#25 bit 0 = SP2 (1 = scroll across two pages), bit 1 = MSK (1 = mask the
first eight pixels, which is what you want because the left border flips on
every eighth offset).  With SP2 clear the page wraps: the world repeats every
512 pixels.

**Palette (16 entries, 9-bit RGB, 3 bits each component):**

1. R#16 = the colour index (0-15).
2. Write two bytes to port `$9A`: first `0 R2 R1 R0 0 B2 B1 B0`, then
   `0 0 0 0 0 G2 G1 G0`.
3. R#16 auto-increments, so the next pair sets the next colour.

Screen 12 sprites and the screen 10/11 YJK modes are the other V9958-only
features; this port needs neither YJK nor interlace.

## The machine

blueMSX's *MSX2+ - C-BIOS* machine will not start in the bundled libretro
core (the cartridge loads, then `retro_run` never returns - the ship notes a
blocked core).  The *MSX2 - C-BIOS* machine does start, and its `config.ini`
accepts a V9958:

    [Video]
    version=V9958
    vram size=128kB

which is a real combination (several MSX2 machines shipped with a V9958
fitted), so that is the machine the browser build will use, named
`MSX2 - C-BIOS - V9958` under `web/core/bios/Machines/`.

The C-BIOS ROMs in that folder are built from source rather than downloaded,
with the sjasmplus already used for the game:

    tools/build_cbios.sh            # needs sjasmplus and a c-bios checkout

`main_msx2`, `logo_msx2`, `sub` and `music` assemble clean with
`sjasmplus --raw=...` (version 1.24.1), giving 32 KB + 16 KB + 16 KB + 16 KB.

Open question: with the MSX1 cartridge loaded, that machine boots but the
node check stalls before the first screenshot, while a three-byte cartridge
runs for 240 frames.  That is the first thing to debug when the V9958 work
starts - most likely the game's polling of the VDP status register or a
register write the V9938/9958 treats differently (R#1 bit 3, the MSX1
Graphics II bit, is not a screen mode bit on these chips).

## What has to be written

1. **`tools/msx.py`**: a V9958 alongside the TMS9918A - 128 KB VRAM, a
   17-bit address counter with R#14 as the page, registers 0-27, the palette
   port, GRAPHIC 6 rendering with R#23/R#26/R#27 offsets, sprite mode 2.
2. **`dino.asm`**: the display layer.  The game logic (physics, obstacles,
   score, modes, music driver, sounds) carries over; the tile engine does not.
   Sky, sand, the ground texture, the moon, the stars and the logo become
   bytes we write ourselves; the HUD is either redrawn at `x + HSCR` every
   frame on the solid sky, or the screen is split with the line interrupt
   (R#19) so the HUD can sit in a band that never scrolls.
3. **`tools/gen_gfx.py`**: the same Chromium sheet, cut for the new mode -
   8x8 glyphs, 16x16 sprite patterns in the V9958's layout (two halves of
   sixteen bytes, left then right), and the world strip.
4. **`tools/capture.py`**: its screen assertions are all tile-and-name-table
   based and have to become pixel-and-palette based.

Doing the sprite-pattern layout from the datasheet rather than from memory is
the lesson of the MSX1 round: the quadrants were row-major in the art and in
the emulator, agreed with each other, and were wrong on the chip.
